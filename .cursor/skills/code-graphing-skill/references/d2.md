# D2 Tier

Use this reference after the parent skill selects D2.

## 1. Runtime contract

Pinned renderer: D2 `v0.9.0`.

Required host tools for first setup:

- POSIX shell
- `curl`

The D2 installation is isolated under:

```text
<skill-root>/.diagram-tools/d2/
```

Initialize or verify with:

```bash
scripts/setup.sh d2
```

The bundled executable is:

```text
.diagram-tools/d2/bin/d2
```

D2 natively renders SVG, PNG, PDF, PPTX, GIF, ASCII, or stdout. PNG rendering has no external browser dependency.

`scripts/render-d2.sh` passes **`--theme=200`** (dark) by default. Override with e.g. `--theme=0` after the output path. Font defaults to D2’s bundled Source Sans Pro unless you pass `--font-regular`.

## 2. Use D2's richer primitives deliberately

D2 is the complex tier because it can preserve richer composition and output behavior. Do not reproduce Mermaid syntax mechanically.

### Containers

Use containers for actual architectural, ownership, package, phase, or trust boundaries. Nest only when the nesting answers the diagram question.

### Shapes and semantic types

Choose shapes by meaning and keep the vocabulary small. Use D2's structured forms when they materially improve comprehension:

- SQL tables for schemas/ERDs;
- UML classes for type structure;
- sequence diagrams for interactions;
- Markdown or code blocks for concise evidence/context;
- grids when a repeated matrix layout is itself meaningful.

### Connections

Every important connection should communicate a relationship. Label protocol/event/action/data when direction alone is insufficient. Use line/arrow styles to distinguish semantics only when a legend is unnecessary or obvious.

### Classes and globs

Define reusable semantic classes instead of repeating styles. Apply globs/classes to coherent categories. Keep source semantics legible even when all styling declarations are ignored.

## 3. Layout strategy

D2 supports multiple layout engines. Start with the default `dagre` because it is fast and hierarchical.

Use `elk` when dense directed graphs, nested containers, or edge routing are materially clearer with it:

```bash
scripts/render-d2.sh diagram.d2 diagram.svg --layout=elk
```

Use TALA only when it is actually installed/available and its architecture-specific placement features are required. Never make a deliverable depend on an unavailable optional engine.

Do not force dimensions or placement before restructuring the graph. When edges are crowded around small nodes, increasing node dimensions can improve routing, but this is a late-stage layout correction.

## 4. Interactivity

D2 SVG can contain interactive behavior such as links and tooltips.

Use tooltips for secondary detail that would clutter the main diagram. Use links when a node/edge should navigate to documentation, source, or another board.

Interactivity depends on how the SVG is embedded. Inline SVG, `<object>`, `<iframe>`, or `<embed>` can preserve links; an `<img>` embedding generally does not. PNG cannot preserve interactivity, so D2 adds appendix-style representations for links/tooltips in static output.

If interactivity matters, deliver the SVG itself in addition to any PNG.

## 5. Composition: layers, scenarios, steps

Use multiple boards only when there is genuine change or alternate context.

- **`layers`** — independent boards that do not inherit from the base. Use for different views or conceptual layers.
- **`scenarios`** — boards that inherit from the base. Use for alternatives or variants of one baseline.
- **`steps`** — each board inherits from the previous step. Use for progressive build-up, algorithms, migrations, or time-ordered change.

Keep board identity stable so viewers can track what changed.

### Multi-board output paths

When the source defines multiple boards (`layers`, `scenarios`, or `steps`), a render target like `<chart-slug>.svg` may create board files under that slug folder. Normalize to the parent skill bundle: copy `index.svg` → `<chart-slug>.svg` and `index.png` → `<chart-slug>.png`, keep extra board files alongside when useful. `scripts/render-d2.sh` reports when a multi-board directory was emitted.

## 6. Animation and dynamic output

For multi-board content, D2 can package boards into a single animated SVG or GIF.

Animated SVG:

```bash
scripts/render-d2.sh diagram.d2 diagram.svg --animate-interval=1200
```

Animated GIF:

```bash
scripts/render-d2.sh diagram.d2 diagram.gif --animate-interval=1200
```

Use animation only when motion communicates change, sequence, or comparison better than adjacent static views. Avoid animation for a static architecture merely because the renderer supports it.

SVG is the preferred "true object" deliverable for interactive or animated diagrams. GIF is a compatibility fallback without SVG interactivity.

## 7. Live browser preview

For iterative visual work, use D2 watch mode:

```bash
scripts/preview-d2.sh path/to/diagram.d2 path/to/diagram.svg
```

This runs D2 watch mode and opens the configured local browser with live reload. The process is intentionally foreground/interactive; stop it when inspection is complete.

If automatic browser launch is inappropriate, run the local D2 binary with `--watch --browser=0` and open the served URL manually.

## 8. Rendering

From **skill root**, write into **workspace** bundle paths:

```bash
scripts/render-d2.sh "<workspace>/diagrams/<chart-slug>/<chart-slug>.d2" \
  "<workspace>/diagrams/<chart-slug>/<chart-slug>.svg"
scripts/render-d2.sh "<workspace>/diagrams/<chart-slug>/<chart-slug>.d2" \
  "<workspace>/diagrams/<chart-slug>/<chart-slug>.png"
```

Pass renderer options after the output path:

```bash
scripts/render-d2.sh diagram.d2 diagram.svg --layout=elk --pad=40
```

Each chart bundle requires **source + SVG + PNG** unless the user waives a format. Use GIF/PDF/PPTX only when the user requests that destination or animation replaces static multi-board PNG/SVG.

## 9. Validation loop

Before rendering, format/check source when appropriate (from skill root):

```bash
.diagram-tools/d2/bin/d2 fmt --check diagram.d2
.diagram-tools/d2/bin/d2 fmt diagram.d2
```

On Windows, Git Bash resolves `.diagram-tools/d2/bin/d2` to `d2.exe` when present.

A successful render is necessary but not sufficient. Inspect the output and verify:

- graph semantics match verified source material;
- containers are meaningful and not decorative;
- edge routing does not obscure relationships;
- labels fit without excessive whitespace;
- interactive affordances are discoverable when used;
- multi-board transitions preserve enough stable context to compare states;
- animations remain understandable when paused on any board.

Fix in this order:

1. scope;
2. graph structure;
3. grouping;
4. layout engine;
5. dimensions/wrapping;
6. styling.

## 10. Output contract

Use the parent skill workspace layout: `<workspace>/diagrams/<chart-slug>/` with `<chart-slug>.d2`, `<chart-slug>.svg`, and `<chart-slug>.png` for every chart. Point the user to those workspace paths in the reply.

For animation-only deliverables, a single animated `<chart-slug>.svg` (and optional `.gif`) may supplement the bundle when motion is required; still keep the `.d2` source in the same folder.
